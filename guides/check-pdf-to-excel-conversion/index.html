How to check that a PDF-to-Excel conversion is correct (5 quick checks)

Converting a PDF to Excel is the easy part. The risky part is a number that was misread, a row that was dropped, or an amount that landed in the wrong column and nobody notices until the totals are wrong. Bank statements, supplier invoices and price lists have built-in redundancy, so you can test the result in about five minutes.

These checks assume the data is in a normal table: headers in row 1, data starting in row 2, and the last data row at 100 (change 100 to your last row).

First: try Excel's own converter

If your PDF is a clean, text-based document (you can select the text with your mouse), Excel for Microsoft 365 on Windows can read it directly: Data > Get Data > From File > From PDF. Pick the table in the Navigator, then Load. Availability depends on your Excel version, so check the Data tab. It often works well for simple tables and struggles with tables that span pages, merged cells and scans. Whatever tool you use, run the checks below.

Check 1: Does the row count match?

Count the transactions or line items on the PDF (many statements and price lists print an item count; invoices have a line count you can count by hand). In Excel: =COUNTA(A2:A100) on a column that is never blank, such as the date or SKU. A difference means dropped or merged rows.

Check 2: Do the totals match what is printed?

Compare the sums with the totals printed on the document:

=SUM(C2:C100)    total debits (or line amounts)
=SUM(D2:D100)    total credits
=E100            closing balance (last row)

If a printed total is not equal to your sum, look at the pages where the numbers contain commas, brackets or minus signs. Those are the usual places for misreads.

Check 3: Does the running balance chain hold? (statements)

Each printed balance should equal the previous balance minus the debit plus the credit. Put your opening balance in G1 and use:

First row:   =G1-C2+D2-E2
All others:  =SUMPRODUCT(--(ABS(E3:E100-(E2:E99-C3:C100+D3:D100))>0.005))

Both should return 0. The second formula counts rows where the chain breaks. A broken row means a misread amount in that row or in the one above. Blank cells count as 0; if your blanks are text such as "-" or "", convert them to true blanks first. On a small test statement we built, the correct file returned 0, and changing one balance by one dollar made the formula report exactly 1 broken row.

For invoices the same idea applies: quantity × unit price = amount for each row, and the amounts should add up to the subtotal.

Check 4: Are the numbers really numbers?

Numbers stored as text will not add up and will quietly be left out of sums. This returns how many cells in your amount columns are text:

=COUNTA(C2:E100)-COUNT(C2:E100)

It should be 0. If not, the usual causes are trailing spaces, a stray currency symbol, or brackets used for negatives. Text-to-columns or =VALUE(TRIM(C2)) fixes most of them. Do the same for dates: select the date column and sort. If the dates do not sort in calendar order, some are text.

Check 5: Spot-check by eye

Open the PDF next to the sheet and compare the first and last row of every page, plus five random rows. Page breaks are where tables get split, repeated headers sneak in as data rows, and multi-line descriptions turn into extra rows.

What these checks cannot do. A pass shows the spreadsheet agrees with itself and with the totals printed on the PDF. It does not prove the PDF is right. If two errors cancel each other out, the totals still match, which is why Check 5 is there. Scanned pages, handwriting and poor photos need a different process and a human eye on every number.
